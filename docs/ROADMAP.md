## Current-state verdict

### What is already substantial

Intrilex already includes:

- Complete human-playable Advanced and Unrestricted Core profiles.
- Local play against multiple AI policies.
- Deterministic replay generation and verification.
- Decision traces and policy diagnostics.
- Paired counterfactual branches.
- Mechanics, synergy, rank, evidence, comparison, and history workspaces.
- Server-authoritative online 1v1.
- Ranked matchmaking, seasons, placements, ratings, profiles, rivals, and leaderboards.
- Spectator support.
- Academy and puzzle systems.
- Tournament domain and UI work.
- Replay Caster with Ollama commentary, theatre playback, public/omniscient viewing, and `WAIT WHAT?`.
- Player strategic fingerprints and meta reporting.
- A large automated verification suite.

The implementation's scope is much newer than parts of its outward documentation. For example, `README.md` and `KNOWN_LIMITATIONS.md` contain claims inherited from earlier network stages, while the current application has ranked accounts, seasons, public matchmaking, tournament work, and considerably more. That documentation drift should be treated as a product defect.

### What is presently blocking trustworthy expansion

The latest balance pass found that the game design itself does not presently justify numerical balance changes. The main problems are implementation and evidence quality:

- `IMPL-01`: scoring riders block Seven, `10♣`, and Black Joker scoring.
- `IMPL-12`: declaration-class counter authority is wrong or incomplete.
- `DEG-01`: Sudden Death declaration and countdown are defective.
- `IMPL-03`: ⭐6 and ⭐7 legal-choice enumeration is incomplete.
- `IMPL-04`: resolved `10♦` reaches the wrong destination.
- `AUTH-04`: the rank/engine capability registry overstates or misstates some executable paths.
- `POL-A1`: Solo Wild and Wild Sovereignty lack adequate AI valuation.
- `POL-A2`: policies spend reactive cards without enough retention awareness.
- `POL-A3`: flat heuristic bonuses cause disproportionate 3-Red Ultra activation.

The result is a crucial distinction:

> Intrilex's central mechanics appear healthy, but some of the evidence describing their balance was generated by an incomplete executable interpretation and shallow policy behavior.

That means **engine correctness precedes balance tuning**, and **policy correction precedes broad empirical claims**.

# Phase 1 — v0.28.1: Rules-Parity Hotfix

**Target:** First engineering milestone
**Effort:** 1–2 weeks
**Priority:** P0

This is the one genuinely non-negotiable phase.

## 1. Repair special scoring paths

Implement the full written scoring contracts for:

- Any Seven:
  - scores its normal seven Points;
  - triggers the appropriate reveal/take rider;
  - preserves exact stack and trigger timing.
- `10♣`:
  - scores ten Points;
  - receives its entry protection;
  - performs the zero-Points bonus-scoring path correctly.
- Black Joker:
  - scores eleven Points;
  - performs its required recycling/destination behavior;
  - remains distinct from Board Lock.

Do not implement these as exceptions scattered through the UI and engine. Introduce a canonical scoring-rider pipeline:

```text
validate score declaration
→ place/score source card
→ apply printed scoring value
→ create canonical rider trigger
→ open required response/choice windows
→ resolve destination and protection
→ certify terminal state
```

### Acceptance gates

- All three scoring actions appear in legal-action enumeration.
- They execute through the same authority used by local, AI, network, and replay paths.
- Human, AI, replay, and network behavior agree.
- Privacy projections never expose rider choices early.
- Save/resume during rider choice is deterministic.
- Existing ordinary scoring remains unchanged.
- The current diagnostic probe no longer reports `CORE_SCORING_RIDER_UNSUPPORTED`.

## 2. Replace ad hoc counter classification with an authority matrix

The report's `IMPL-12` should not be fixed with a narrow string-list patch alone. Establish a declaration-class matrix defining which response authorities can answer which declaration types.

For example:

| Declaration class | Base Ace | A♠ | K | K♠ | ⭐A / 3-Red | Special restrictions |
|---|---:|---:|---:|---:|---:|---|
| Ordinary effect | Canonical | Canonical | Contextual | Contextual | Canonical | Guard/Aegis where relevant |
| Rank-10 solo effect | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Rank-10 limits |
| Super | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Multi-card source handling |
| Ultra | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Exact Ultra authority |
| Queen's Court | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Multi-play classification |
| Royal Marriage | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Multi-play classification |
| Board Lock | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Explicit authority only |
| Sudden Death | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Per rulebook | Exact recipe/source semantics |

The point is to make counter authority **data-testable**, rather than dependent on fragile names such as `ordinary-effect` and `rank10`.

### Acceptance gates

- A table-driven test covers every declaration class × counter authority pair.
- Negative cases are tested as rigorously as positive cases.
- Source-card disposition is correct when a declaration is countered.
- Counter-counter chains remain deterministic.
- Local, browser worker, network server, replay, and branch simulations agree.

## 3. Repair Sudden Death completely

The current probe confirms that Sudden Death:

- is offered without required source cards;
- consumes a Mini-Turn;
- remains stuck at three after twelve completed turns;
- never produces a terminal result.

The repair must cover the entire lifecycle:

- Require canonical recipes: Red Joker + Black Joker or four-of-a-kind, as governed by the rulebook.
- Include exact source cards in the declaration.
- Open the correct counter window.
- Move committed cards to their canonical destinations.
- Record activator and activation boundary.
- Decrement only on the correct completed Full-Turn boundaries.
- Handle skipped turns and incomplete turns correctly.
- Produce an authoritative winner or terminal reason.
- Save, resume, replay, branch, and reconnect across the active timer.
- Ensure Caster and spectators receive only authorized state.

### Acceptance gates

- No zero-source Sudden Death action can be enumerated.
- Countdown behavior is fixture-tested across ordinary, skipped, interrupted, and resumed turns.
- Terminal outcome is deterministic.
- Network reconnect during Sudden Death reproduces the exact timer.
- Replay certification includes the timer transition history.

## 4. Close ⭐6, ⭐7, and `10♦` correctness

- Complete ⭐6 and ⭐7 legal-choice enumeration.
- Test empty, partial, maximum, and stale-choice cases.
- Route `10♦` to Exile when its Mimic resolution requires that destination.
- Verify copied effects do not overwrite the printed identity or source provenance.
- Check save/replay serialization for generated choices and copied effects.

## 5. Reconcile the capability registry

The current capability manifest can be internally valid while advertising modes that do not have complete executable paths.

Make the registry derive from one canonical contract:

```text
profile
→ declaration family
→ executable enumerator
→ resolver
→ response authority
→ privacy projection
→ replay serializer
→ AI support
→ certification fixtures
```

A family should be called `SUPPORTED` only when all required columns are closed. Otherwise it should be `PARTIAL`, `HUMAN_ONLY`, `REPLAY_ONLY`, or `BLOCKED` with an explicit reason code.

## 6. Repair immediate AI blind spots

Before generating new balance evidence:

- Give Solo Wild and K♠ Wild Sovereignty explicit, explainable valuation.
- Add retained-counter value for Aces, Eights, and other reactive cards.
- Penalize low-value reactive firing.
- Make 3-Red Ultra valuation depend on the declaration being answered and the hand opportunity cost.
- Preserve deterministic scoring and decision-trace decomposability.

Do not jump directly to a black-box learned model. First make the existing heuristic agent reason correctly about the rules it already sees.

## Phase 1 exit gate

- All seven Priority-A recommendations in the balance report are resolved.
- New targeted fixtures pass.
- Full suite passes with zero failures.
- Build, lint, typecheck, determinism, privacy, release identity, engine manifest, and clean-room gates pass.
- Browser and server use the same repaired authority.
- No numerical card balance changes have been introduced.
- A `v0.28.1` repair ledger maps every finding to code, tests, and outcome.

# Phase 2 — v0.28.2: Evidence Recalibration

**Target:** Immediately after the correctness hotfix
**Effort:** 1–2 weeks
**Priority:** P0/P1

Once engine semantics are repaired, the previous empirical dataset becomes a historical baseline. Do not quietly mix pre-fix and post-fix matches.

## Major changes

### 1. Version the evidence epoch

Every generated match, trace, result, and report should carry:

- engine version and authority hash;
- rules version;
- profile ID;
- policy ID and policy-version hash;
- seed;
- seat assignment;
- experiment ID;
- evidence epoch;
- whether it was created before or after the rules-parity repair.

### 2. Generate a clean Unrestricted corpus

The current 100-match Advanced corpus is useful descriptive evidence, but insufficient for Unrestricted or human-meta conclusions.

Generate:

- Balanced AB/BA seat swaps.
- Equal policy-pair representation.
- Self-play excluded from cross-policy superiority claims.
- Enough samples for the stated uncertainty targets.
- Dedicated coverage for rare mechanics rather than hoping they emerge naturally.
- Separate natural-frequency and forced-fixture datasets.

### 3. Execute the seven proposed experiments

The current investigation already proposes the right next experiments:

1. Early 2B2R Ultra activation versus component retention.
2. Board Lock while ahead versus behind.
3. `10♥` Tempo Spike versus scoring ten Points.
4. Two-Queen fortress breach rate.
5. Total Clear as comeback mechanism versus win-more mechanism.
6. Unrestricted seat balance after correctness closure.
7. Counter-retention policy versus immediate reactive firing.

Do not collapse these into a single aggregate win-rate table. Preserve:

- decision-level comparisons;
- matched continuations;
- confidence intervals;
- opportunity frequency;
- activation frequency;
- conversion;
- counter availability;
- seat effects;
- policy effects;
- exact replay anchors.

### 4. Introduce policy-strength tiers

Intrilex needs explicit labels for what a policy is evidence-capable of demonstrating:

- **Fixture policy:** tests legality, not strategy.
- **Baseline policy:** creates reproducible behavior.
- **Heuristic policy:** makes locally informed choices.
- **Lookahead policy:** evaluates limited continuations.
- **Tournament policy:** passes defined competitive benchmarks.
- **Human-meta proxy:** not currently established.

This prevents "experienced AI" from becoming an unmeasured marketing term.

## Minor changes

- Add corpus comparison views: pre-fix versus post-fix.
- Show missingness directly in rank and mechanic reports.
- Flag conclusions invalidated by engine or policy changes.
- Add a "why this evidence is admissible" disclosure to public-facing reports.
- Store experiment presets so they are reproducible from the UI.
- Support cancel/resume for long experiment runs without corrupting cohort identity.

## Exit gate

- The balance investigation is regenerated against the repaired engine.
- Pre-fix and post-fix evidence are never silently combined.
- Unrestricted simulation readiness advances from `PARTIAL` only if every required authority and coverage gate actually passes.
- Every watchlist item is strengthened, weakened, or remains unresolved using its predeclared falsification criterion.
- Balance changes remain off the table unless post-repair evidence supports them.

# Phase 3 — v0.29.0: Product Truth & Release Candidate

**Target:** After evidence restoration
**Effort:** 1–2 weeks
**Priority:** P1

Intrilex's software has outrun its documentation and information architecture. The next major release should make the product understandable and honestly releasable.

## Major changes

### 1. Establish one generated capability truth

Generate the following from the same machine-readable capability contract:

- README capability summary.
- Known Limitations.
- In-app mode badges.
- Setup-screen availability.
- Release manifest.
- Deployment checklist.
- Public feature matrix.
- Test-coverage requirements.

This prevents contradictions such as:

- old invite-only networking language alongside ranked public queues;
- "no accounts" alongside Supabase-backed ranked identity;
- stale version histories presented as current release summaries;
- optional modules and multiplayer being conflated with supported online 1v1.

The current `docs/CAPABILITY_MATRIX.md` is a good foundation, but it should become generated or programmatically verified rather than manually reconciled.

### 2. Reframe the product into three lanes

The present surface area is powerful but cognitively expensive. Organize it around:

```text
PLAY
Local, ranked, tournaments, replays

LEARN
Academy, puzzles, rules, card reference

LAB
Watch, Caster, mechanics, ranks, evidence,
traces, branches, diagnostics, Brain
```

Keep advanced tools available, but stop making every workspace compete equally for attention.

### 3. Pay down high-risk monoliths

The largest live source files include:

- `app.js` — approximately 130 KB.
- Ranked duel renderer — approximately 120 KB.
- Observatory workspace — approximately 103 KB.
- Play controller — approximately 98 KB.
- Match server — approximately 96 KB.
- Profile workspace — approximately 88 KB.

Decompose by responsibility, not arbitrary line count:

- routes and lifecycle;
- state/view-model construction;
- rendering;
- events;
- persistence;
- network session;
- domain services;
- analytics adapters.

For `server.mjs`, move protocol handlers and services behind narrowly typed boundaries. For UI monoliths, preserve behavior with characterization tests before extraction.

### 4. Upgrade tests from source-shape checks to behavior

Some newer tests assert that particular strings or imports exist. Those are useful scaffolding checks but weak protection against runtime defects.

Shift critical journeys toward behavioral browser tests:

- create and finish a local match;
- save and resume;
- reconnect to an online match;
- join and leave ranked queue;
- spectate without hidden-information leakage;
- finish placement and inspect rating change;
- complete Academy lesson;
- open, play, seek, and investigate a Caster replay;
- navigate the Brain using mouse and keyboard;
- reload every primary route directly.

### 5. Run production-shaped certification

Before declaring `v0.29.0` an RC:

- Fresh install from the lockfile.
- Build twice and compare deterministic outputs.
- Full CI on Windows and Linux.
- Real-browser tests at 1920×1080, 1440×900, 1366×768, tablet, and mobile.
- Production-mode match server.
- Auth-required ranked admission.
- Database backup and restore drill.
- Terminal-outbox restart recovery.
- WebSocket reconnect and backpressure stress.
- Secret containment scan.
- Replay compatibility migration test.
- Accessibility pass with keyboard-only and reduced motion.

## Minor changes

- Replace stale version prose with a concise current-version summary and links to history.
- Merge duplicate third-party notice files if their contents can be safely reconciled.
- Document generated versus authored artifacts.
- Reduce existing lint-warning debt in bounded batches.
- Add bundle budgets, especially around Three.js, Supabase, Play, and Caster chunks.
- Ensure local database files and environment material remain ignored and absent from packages.
- Make empty, loading, offline, and degraded states consistent across workspaces.

## Exit gate

- A new user can accurately explain what Intrilex is after seeing the landing page.
- Every visible feature claim is linked to a tested capability.
- No stale "planned" UI remains for features that already exist.
- Production setup can be executed from documentation without repository archaeology.
- No P0 or P1 correctness/security/privacy issue remains.
- The RC is cut from a clean tree.

# Phase 4 — v0.30.0: Player Experience

**Target:** Once the product is truthful and stable
**Effort:** 2–4 weeks
**Priority:** P1/P2

This phase should make the game more pleasurable to play—not merely add more things.

## Major additions

### 1. Finish the game-start experience

The existing polish report identifies the Play landing page and new-game setup as unfinished. Complete:

- Clear Local, Ranked, Academy, Tournament, and Replay choices.
- Rule-profile explanation in player language.
- AI difficulty descriptions based on measured behavior.
- Seed controls hidden under Advanced options.
- Resume/reconnect surfaced before new-match creation.
- Compatibility warnings before loading old saves or replays.

### 2. Build the full semantic action presentation system

Introduce consistent effects for:

- declaration;
- response window;
- counter;
- counter-counter;
- resolution;
- fizzle;
- score;
- control change;
- protection gain/loss;
- terminal victory.

Animations should consume semantic engine events, never infer game truth from DOM differences.

Requirements:

- Reduced-motion equivalents.
- Adjustable intensity.
- No animation may delay canonical processing.
- Replay and live matches share presentation semantics.
- Caster can stretch presentation timing without altering match state.
- Complex Stack resolution remains readable at higher playback speeds.

### 3. Turn the Card Inspector into an educational bridge

For any visible card, show:

- printed identity and Points value;
- currently legal uses;
- unavailable uses and exact reason;
- protection and targeting status;
- relevant timing windows;
- concise rule reference;
- Academy lesson or puzzle link;
- Mechanics/Rank Anatomy link in Lab mode.

This is higher-value than adding another separate analysis page.

### 4. Finish layout customization

The existing architecture already anticipates presets. Add:

- Compact, Broadcast, Tactical, and Accessibility layouts.
- Persistent module visibility and panel sizing.
- Reset-to-default.
- Per-device layout storage.
- Import/export only if the schema is stable.
- A safe banner/cosmetic system after upload validation exists.

### 5. Academy progression refinement

Academy already exists; deepen it instead of rebuilding it:

- Allow explanation-first completion for players stuck on a lesson.
- Separate "understood the mechanic" from "won the match."
- Add mastery challenges based on exact mechanics.
- Let puzzle performance recommend lessons.
- Explain mistakes using deterministic legal alternatives.
- Avoid AI-authored rules unless the response is grounded in canonical rule references.

## Minor additions

- Better mobile card zoom and target confirmation.
- Undo only before authoritative submission, never after.
- Improved rematch flow and opponent status.
- Consistent keyboard shortcuts.
- Color-blind-safe suit and state identifiers.
- Adjustable log density.
- Search across rules and cards.
- Better replay annotations/bookmarks.
- Exportable post-match summary image.
- Optional custom banners after MIME, size, decoding, storage, and privacy safeguards are defined.

## Exit gate

- A new player can start, understand, finish, and review a match without opening the developer Observatory.
- Advanced players can still reach deep evidence in one or two actions.
- Target selection and response windows are unmistakable.
- All significant state changes have accessible non-animation representation.
- Usability testing produces no recurring "I don't know what the game wants me to do" failure.

# Phase 5 — v0.31.0: Competitive Operations

**Target:** After player UX stabilization
**Effort:** 3–6 weeks
**Priority:** P1

Most ranked foundations already exist. The work now is operational credibility.

## Major additions and changes

### 1. Finish production deployment as a tested product

- Formal staging and production environments.
- Database migrations with forward and rollback procedures.
- Rotating secrets and least-privilege service roles.
- Automated backups plus scheduled restore verification.
- Structured logs and alert thresholds.
- Match capacity and latency dashboards.
- Health endpoint that distinguishes process health, database health, auth health, and queue health.
- Abuse-rate limiting verified under realistic proxy configuration.

### 2. Prove ranked integrity end to end

- Server-owned queue, profile, season, and match classification.
- Durable result/rating idempotency.
- No double rating after retry or reconnect.
- No rating if a terminal result is unverified.
- Clear handling for disconnect, abandonment, server failure, and invalid client commands.
- Season rollover tested against live-shaped data.
- Placement and leaderboard calculations reproducible from stored results.
- Public explanation of Glicko-2 uncertainty without drowning players in math.

### 3. Complete human tournament infrastructure

The tournament domain is broad, but server-side operation should remain bounded:

- Registration.
- Check-in.
- Seeding.
- Bracket generation.
- Match scheduling.
- Result authority.
- BYEs.
- Disconnect rulings.
- Tournament resumption after restart.
- Admin correction with immutable audit history.
- Single-elimination first; Swiss only after pairing constraints and tiebreakers are fully specified.

Do not market tournament scaffolding as a production tournament platform until this lifecycle is closed.

### 4. Improve spectator and broadcast flow

- Spectator discovery and invitations.
- Delayed public broadcast when hidden-information risk warrants it.
- Public versus judge/omniscient projection contracts.
- Match status and reconnect state.
- Caster handoff from a completed authoritative match.
- Replay download and evidence links.
- Tournament-bracket-to-broadcast navigation.

### 5. Add lightweight social safety

Because chat, rivals, public profiles, and matchmaking introduce people—not just software:

- Block and report flows.
- Muting.
- Display-name validation.
- Chat rate limits.
- No exposure of account identifiers in public projections.
- Moderator audit log.
- Clear retention policy.
- Minimal permissions and no speculative community system.

## Minor additions

- Queue estimates based on real samples instead of fixed claims.
- Region or latency display only when measured reliably.
- Recent-opponent rematch constraints.
- Shareable match and tournament links.
- Maintenance mode.
- Season countdown.
- In-client status banner for degraded services.
- Operator dashboard for stuck outbox jobs and orphaned matches.

## Exit gate

- A staging season can run from provisioning through archival without manual database intervention.
- Server restart does not lose matches, ratings, tournament state, or terminal effects.
- Backup restoration is demonstrated.
- Ranked exploits have a documented threat model and regression suite.
- Operational documentation matches deployed topology.

# Phase 6 — v0.32.0: Intelligence, Better AI, and Replay Caster v1

**Target:** After engine and competitive truth are stable
**Effort:** 2–4 weeks
**Priority:** P2

This is where Intrilex becomes uniquely itself again.

## 1. Develop a bounded lookahead policy

The current forensic work shows that one-ply utility is insufficient for:

- preserving counters;
- valuing latent threat;
- comparing scoring with tempo;
- holding combo pieces;
- assessing Board Lock;
- recognizing fortress escape routes.

Add a deterministic bounded-search policy:

```text
candidate action
→ exact engine continuation
→ opponent response set
→ short deterministic horizon
→ terminal/resource/position evaluation
→ uncertainty and budget report
```

Guardrails:

- Fixed node/time budgets.
- Deterministic tie-breaking.
- Search metadata stored in decision traces.
- No hidden-information access beyond the policy's authorized projection.
- Separate evaluation function from search mechanics.
- Compare against current heuristics with matched AB/BA experiments.

Do not call it expert until it passes a published benchmark suite.

## 2. Harden Replay Caster's commentary contract

Replay Caster is strategically valuable, but its most important property is not "AI commentary." It is **evidence-backed passive observation**.

Develop:

- Stronger structured-output validation.
- Fact-level authorization rather than only lexical spoiler checks.
- Explicit public, participant, judge, and developer context schemas.
- Versioned prompt and model provenance.
- Commentary caching keyed by replay, beat, viewer mode, prompt version, and model.
- Deterministic event labels when Ollama is unavailable.
- Cancellation and retry without replay disruption.
- Better handling of malformed streaming output.
- Clear indication of generated commentary versus deterministic facts.

The commentator may explain diagnostics, but it must never become the diagnostic authority.

## 3. Complete `WAIT WHAT?` as an investigation workflow

Turn the existing capture into:

```text
bookmark suspicious moment
→ preserve authorized before/after context
→ inspect legal alternatives
→ open exact decision trace
→ branch runner-up action
→ compare matched outcomes
→ annotate conclusion
→ export investigation envelope
```

Useful additions:

- User-written note.
- Severity/category tag.
- Shareable redacted package.
- "Confirmed defect," "policy oddity," "legal but surprising," and "insufficient evidence" dispositions.
- Link back from the finding to replay, beat, decision, branch, and engine version.
- Automatic invalidation when the engine authority hash changes.

## 4. Decide the Brain's actual job

The 3D Brain is visually interesting, but it should earn its place. Choose one primary purpose:

- onboarding map;
- mechanic-relationship explorer;
- evidence topology;
- live match-state graph;
- development architecture viewer.

My preference is **mechanic/evidence topology**, not a general homepage spectacle. A graph becomes valuable when it answers:

> "What interacts with this mechanic, which cards provide it, what counters it, and what evidence supports those relationships?"

Provide a complete 2D/list equivalent. Three-dimensional presentation should be optional enrichment, never the only navigable structure.

## 5. Make player intelligence evidence-honest

Strategic fingerprints and meta reports should distinguish:

- descriptive labels from skill claims;
- insufficient sample size;
- policy or rules-version changes;
- season boundaries;
- local versus ranked matches;
- mirror versus asymmetric matchups;
- human versus AI evidence.

A player with five matches should not receive the same certainty-laden archetype presentation as one with five hundred.

## Optional later addition: local TTS

TTS comes after textual commentary is correct:

- asynchronous;
- cancellable;
- cached;
- optional;
- does not block playback;
- accessible subtitles always remain available;
- voice output never receives extra hidden information beyond the validated commentary text.

## Exit gate

- Lookahead policy measurably outperforms or meaningfully differs from heuristic baselines without privacy violations.
- Caster output cannot bypass the authorization layer.
- Every commentary or investigation item retains provenance.
- `WAIT WHAT?` can move from suspicion to engine-backed evidence.
- Intelligence labels communicate uncertainty honestly.

# Phase 7 — v1.0.0: Certified public baseline

Intrilex should reach `1.0` when it is **stable enough to be trusted**, not when every possible module exists.

## Required v1.0 gates

### Rules and engine

- All advertised two-player rules execute exactly as the governing rulebook specifies.
- Every declaration family has legality, resolution, counter, destination, replay, privacy, and AI coverage.
- Rulebook, engine, manifest, UI, and release documentation agree.
- No known P0/P1 rules-parity defect.
- Balance findings have been rerun after correctness repairs.

### Local player experience

- New player onboarding is complete.
- Local AI matches, saves, resumes, imports, exports, and replays are stable.
- Old data either migrates or fails with a clear compatibility explanation.
- Keyboard, mobile, reduced-motion, and high-contrast experiences are certified.

### Online experience

- Ranked season lifecycle is proven.
- Auth, reconnect, matchmaking, spectator projection, ratings, results, outbox recovery, backup, and monitoring are production-tested.
- Abuse controls exist.
- Privacy threat model is current.
- Failure states are player-readable.

### Laboratory

- Replays, traces, counterfactuals, diagnostics, and reports are linked by stable identifiers.
- Every analytical conclusion records its evidence epoch and limitations.
- Generated reports can be reproduced.
- Stale conclusions are visibly invalidated after authority changes.

### Release engineering

- Clean-room install and build.
- Deterministic build verification.
- Full CI on supported environments.
- Real-browser E2E.
- Secret scan.
- Dependency audit.
- Artifact inventory and checksums.
- Migration and rollback rehearsal.
- No untracked debug or generated ambiguity in the release tree.

### Human validation

Before `1.0`, conduct several structured sessions with:

- a new player;
- an experienced earlier-version player;
- a systems-minded player;
- the developer acting only as an observer.

Measure:

- Can they start a correct match?
- Do they understand why an action is unavailable?
- Can they recognize priority and response windows?
- Can they recover from disconnection?
- Can they find a replay and inspect a suspicious decision?
- Does the interface teach the game, or does Deffy have to translate it?

That last gate matters. Intrilex should not require its creator standing beside it to become legible.

# Deferred roadmap: deliberately not next

These ideas may eventually be worthwhile, but they should not compete with the preceding work.

## Canonical 3–4 player mode

Keep this blocked until there is an authoritative multiplayer rules contract covering:

- turn and priority order;
- target eligibility;
- alliances;
- hidden information;
- elimination;
- win resolution;
- simultaneous effects;
- spectator projections;
- disconnect handling;
- rating implications.

The repository already labels canonical 3–4 player support as blocked in `docs/CAPABILITY_MATRIX.md`. Do not implement a plausible approximation and call it canon.

## Optional rules modules

Apply the same standard:

- written authority;
- legality enumeration;
- resolution;
- privacy;
- replay;
- AI;
- certification;
- player explanation.

Modules should not be added merely because the engine can be made to accept new action types.

## Mobile-native client

A responsive web/PWA experience should be proven before duplicating the product into native applications.

## Cloud-hosted LLM commentary

Keep Ollama/local commentary as the primary model until:

- consent;
- data minimization;
- hidden-information handling;
- retention;
- cost;
- prompt-injection;
- provider failure

have explicit product contracts.

## Large-scale cosmetic marketplace

Custom banners and skins are reasonable. A marketplace, economy, or monetized inventory system would introduce substantial moderation, account, security, and operational burden without improving the game's foundational legitimacy.

# Major additions versus minor additions

## Major additions worth building

In priority order:

1. Rules-parity repairs.
2. Reproducible post-repair balance evidence.
3. Bounded lookahead AI.
4. Production-shaped ranked operations.
5. Complete server-backed human tournaments.
6. Semantic gameplay presentation.
7. `WAIT WHAT?` evidence workflow.
8. Replay Caster v1 safety and provenance.
9. Unified capability/documentation generator.
10. Event-level canonical state snapshots—only if the engine can expose them without inventing intermediate truth.

## Minor additions worth folding into nearby phases

- Play landing/setup polish.
- Card Inspector improvement.
- Layout presets and persistence.
- Search across cards and rules.
- Replay bookmarks and annotations.
- Better empty/loading/offline states.
- Mobile target confirmation.

- Bundle budgets.
- Lint-debt reduction.
- Generated-artifact cleanup.
- Documentation navigation.
- Optional TTS after commentary safety.
- Custom banners after upload/storage rules.

## Things to avoid

- Numerical balance changes before post-repair experiments.
- More top-level workspaces without consolidating navigation.
- Calling policies "experienced" or "expert" without benchmarks.
- Treating internal manifest verification as rules-parity proof.
- Building 3–4 player behavior from inference.
- Letting the LLM diagnose rules violations directly.
- Mixing evidence from different engine/policy epochs.
- Expanding social features faster than moderation and privacy.
- Adding visual complexity that obscures game-state causality.

# Recommended execution order

```text
Balance artifact closure
        ↓
Rules-parity hotfix
        ↓
Policy baseline repair
        ↓
Evidence regeneration
        ↓
Documentation/product truth
        ↓
Player UX closure
        ↓
Production competitive hardening
        ↓
Lookahead AI + Caster investigation
        ↓
v1.0 certification
```

The hard rule is:

> **No downstream phase may reinterpret a failed upstream gate as "good enough."**

For example:

- If scoring riders are incomplete, do not publish Rank 7 balance conclusions.
- If policy retention is shallow, do not call immediate Ace use strategically optimal.
- If production persistence has not survived restart testing, do not call ranked results durable.
- If a Caster line cannot prove its authorized facts, do not display it as confident analysis.
